# URLFavorites 2.0 (`urlf2`) — 설계 문서

**날짜**: 2026-04-07  
**상태**: 1차 승인  
**대상 도메인**: `https://urlf2.hwandam.kr`

---

## 1. 목표

기존 `https://urlf.hwandam.kr`를 개선한 업그레이드 버전 `urlf2`를 별도 서비스로 구축한다.

`urlf2`는 단순 즐겨찾기 저장소가 아니라, 다음 요구를 만족하는 개인용 지식 아카이브를 목표로 한다.

- 저장은 빠르게
- 다시 찾기는 강하게
- 목록은 답답하지 않게
- 검색은 충분히 강하게
- 모바일 사용성을 우선 고려
- AI 분석 결과 위에 사용자 메모와 컬렉션 맥락을 쌓을 수 있게

---

## 2. 전제와 운영 전략

### 서비스 전략

- `urlf2`는 기존 `urlf`와 완전히 분리된 신규 서비스로 운영한다.
- 기존 `urlf` 데이터는 초기 1회만 이관한다.
- 이관 이후에는 `urlf`와 `urlf2`를 동기화하지 않는다.
- 초기 검수 기간 동안 `urlf`는 유지하되, 실사용 전환은 `urlf2`로 진행한다.

### 사용자 범위

- 개인 전용 서비스로 설계한다.
- 멀티유저, 권한 체계, 공개 공유는 초기 범위에서 제외한다.

### 기술 방향

- 백엔드는 Rails 중심을 유지한다.
- 프론트엔드는 기존보다 더 강한 사용자 경험을 목표로 재설계한다.
- 운영 복잡도는 과도하게 늘리지 않는다.

---

## 3. 핵심 문제 정의

기존 `urlf`에서 가장 크게 개선해야 할 문제는 다음 세 가지다.

- 목록이 답답하다.
- 검색이 약하다.
- 모바일 사용이 불편하다.

따라서 `urlf2`는 저장 그 자체보다 `탐색`, `회고`, `재발견`에 더 강한 구조로 설계해야 한다.

---

## 4. 제품 정의

`urlf2`는 `검색 가능한 카드형 개인 아카이브`로 정의한다.

핵심 개념은 다음과 같다.

- `Favorite`: 저장된 URL 항목
- `Analysis`: AI가 생성한 요약, 태그, 핵심 포인트
- `Tag`: 빠른 분류와 필터를 위한 가벼운 레이어
- `Collection`: 사용자가 명시적으로 묶는 상위 레이어
- `Note`: 사용자가 해당 링크에 남기는 자유 메모

태그와 컬렉션은 역할을 분리한다.

- 태그: AI 중심, 검색 중심, 다중 분류
- 컬렉션: 사용자 의도 중심, 회고 중심, 명시적 정리

---

## 5. UX 원칙

- 저장은 가능한 한 빠르게 끝낸다.
- 탐색은 검색과 필터를 중심으로 강화한다.
- 카드는 시각적 탐색을 돕되, 정보 밀도 높은 리스트 보기로도 전환 가능해야 한다.
- 모바일에서는 데스크톱 레이아웃 축소가 아니라 모바일 전용 흐름을 우선한다.
- 상세 화면은 독립 페이지로 제공해 모바일과 데스크톱 모두에서 자연스럽게 동작하게 한다.
- 메모는 부가 기능이 아니라 핵심 레이어로 취급한다.

---

## 6. 정보 구조

### 6.1 홈 구조

홈은 `검색 중심 아카이브`와 `카드형 컬렉션 보드`를 결합한 하이브리드 구조로 설계한다.

구성은 다음과 같다.

- 상단: 강한 통합 검색바
- 검색바 아래: 빠른 필터 칩
- 본문: 기본 카드형 결과
- 보기 전환: 카드 / 컴팩트 리스트
- 모바일: 동일 정보 구조를 유지하되 필터는 바텀시트 기반

### 6.2 기본 탐색 단위

사용자는 다음 두 축으로 저장 항목을 정리하고 재탐색한다.

- 태그 중심 탐색
- 컬렉션 중심 탐색

즉, `urlf2`는 태그 기반 아카이브이면서 동시에 컬렉션 기반 보드로도 동작해야 한다.

---

## 7. 화면 구조

### 7.1 홈 아카이브

기본 화면은 전체 저장 항목을 검색 가능한 카드형 아카이브로 보여준다.

포함 요소:

- 통합 검색바
- 필터: 태그, 컬렉션, 콘텐츠 타입, 분석 상태
- 정렬: 최신, 최근 분석, 메모 있음, 미분류 등
- 보기 전환: 카드 / 리스트

카드에는 최소한 다음 정보가 보여야 한다.

- 제목
- 소스 또는 콘텐츠 타입
- 대표 이미지 또는 썸네일
- 요약 일부
- 태그
- 메모 존재 여부
- 컬렉션 소속 여부

### 7.2 상세 화면

상세는 사이드 패널 의존형이 아니라 독립 페이지 중심으로 설계한다.

포함 요소:

- 제목, 원본 링크
- 썸네일 또는 대표 이미지
- AI 요약
- 핵심 포인트
- 태그
- 사용자 메모
- 컬렉션 편집
- 재분석 액션
- 분석 메타정보

메모는 상세 하단 부가 섹션이 아니라 비교적 상단에 배치한다.

### 7.3 컬렉션 화면

사용자가 직접 만든 주제 묶음을 보여준다.

예시:

- 읽을 것
- 다시 볼 것
- 사업 아이디어
- AI 리서치

컬렉션 안에서도 검색과 필터가 동작해야 한다.

### 7.4 모바일 저장 흐름

모바일에서는 저장 순간에 과도한 입력을 요구하지 않는다.

흐름:

1. 공유 시트로 URL 저장
2. 항목 생성
3. 선택적으로 메모 추가
4. 나중에 태그 또는 컬렉션 정리

즉, 저장은 빠르게 하고 정리는 후행한다.

## 8. 데이터 모델 방향

### 8.1 favorites

기존 기본 정보에 메모 필드를 추가한다.

권장 필드:

- `url`
- `title`
- `favicon_url`
- `thumbnail_url`
- `content_type`
- `status`
- `raw_content`
- `error_message`
- `retry_count`
- `note`
- `created_at`
- `updated_at`

`note`는 자유 메모 필드로 시작한다.

- 짧은 메모와 긴 메모를 모두 허용한다.
- 개인 전용 서비스이므로 초기에는 별도 노트 모델로 분리하지 않는다.
- 검색 대상에 포함한다.

### 8.2 analyses

기존 분석 모델은 유지하되 `urlf2`에서 검색성과 품질 개선을 위해 계속 활용한다.

포함 요소:

- `summary`
- `tags`
- `key_points`
- `sentiment`
- `transcript`
- `subtitle_source`
- `video_metadata`
- `model_used`
- `analyzed_at`

### 8.3 collections

사용자 정의 컬렉션 엔티티를 추가한다.

권장 필드:

- `name`
- `description`
- `created_at`
- `updated_at`

### 8.4 collection_memberships

하나의 즐겨찾기가 여러 컬렉션에 속할 수 있어야 한다.

권장 구조:

- `favorite_id`
- `collection_id`

### 8.5 태그 처리

- 초기에는 `analyses.tags` JSON 구조를 유지해도 된다.
- 다만 검색 강화를 위해 태그 인덱싱 전략은 초기에 고려해야 한다.
- 필요 시 추후 별도 정규화 모델로 확장할 수 있다.

## 9. 검색 설계

검색은 `urlf2`의 핵심 기능이다.

최소 검색 대상:

- 제목
- AI 요약
- 태그
- 사용자 메모
- 필요 시 원문 일부

필터 조건:

- 태그
- 컬렉션
- 콘텐츠 타입
- 분석 상태

검색 경험 원칙:

- 입력 즉시 결과가 좁혀져야 한다.
- 모바일에서도 같은 검색 경험을 유지해야 한다.
- 카드 보기와 리스트 보기에서 동일한 검색/필터 상태를 공유해야 한다.

---

## 10. 메모 기능 설계

메모는 필수 기능이다.

설계 방향:

- 각 즐겨찾기에 자유 메모를 1개 연결한다.
- 메모는 짧게도, 길게도 쓸 수 있어야 한다.
- 메모 존재 여부를 목록 카드에서 표시한다.
- 상세 화면에서 메모를 쉽게 편집할 수 있어야 한다.
- 모바일 저장 직후 메모를 선택적으로 추가할 수 있어야 한다.
- 검색은 메모 내용을 포함해야 한다.

메모의 역할:

- 왜 저장했는지 기록
- 나중에 다시 볼 포인트 기록
- 개인 해석과 판단 기록

즉, AI 분석 위에 사용자의 해석 레이어를 쌓는 기능으로 본다.

---

## 11. AI 분석 방향

`urlf2`는 UI만 바꾸는 버전이 아니라, AI 분석 파이프라인 개선도 포함하는 업그레이드 버전으로 본다.

유지할 원칙:

- 모든 AI 분석은 비동기 처리
- 재시도 시 `raw_content` 재활용
- llama-server 호출 타임아웃 120초 유지
- 웹페이지와 YouTube 처리 파이프라인 분리

개선 방향:

- 검색 친화적인 요약 품질 개선
- 태그 일관성 개선
- 재분석 흐름 명확화
- 사용자 메모와 AI 분석의 역할 분리

## 12. 데이터 이관 전략

### 12.1 기본 전략

- `urlf` 데이터를 1회만 `urlf2`로 이관한다.
- 실시간 동기화는 하지 않는다.

### 12.2 권장 순서

1. `urlf` 데이터 스냅샷 확보
2. `urlf2` 스키마 생성
3. 기존 `favorites`, `analyses` 변환 이관
4. 태그 정리
5. 기본 컬렉션 정책 적용 여부 검토
6. 샘플 검수
7. `urlf2.hwandam.kr` 배포
8. 실사용 전환

### 12.3 이관 시 고려 사항

- 기존 URL 중복 처리 기준
- 실패 상태 데이터 이관 여부
- 기존 분석 결과를 그대로 보존할지 여부
- 메모 필드는 초기 공백 허용

## 13. 출시 전략

권장 방식은 `병행 오픈 후 짧은 검수`다.

- `urlf.hwandam.kr`: 기존 서비스 유지
- `urlf2.hwandam.kr`: 신규 서비스 배포
- 검수 기간 동안 직접 사용하며 목록, 검색, 모바일 흐름 검증
- 안정화 후 실사용은 `urlf2`로 이동
- `urlf`는 읽기 전용 보관 또는 종료

## 15. Open Questions

아직 확정되지 않은 항목:

- Rails 프론트 레이어를 Hotwire 중심으로 유지할지, 일부를 더 인터랙티브하게 강화할지
- 검색 인덱싱을 SQLite 기본 기능으로 시작할지, 별도 검색 전략을 둘지
- 컬렉션 기본 제공 세트를 둘지, 전부 사용자 생성으로 시작할지
- 기존 `urlf` 분석 결과를 그대로 이관할지, 일부 항목을 재분석할지
- 모바일 저장 직후 메모 입력 UI를 별도 화면으로 둘지, 바텀시트로 처리할지

## 16. 요약

`urlf2`는 기존 `urlf`의 단순 업그레이드가 아니라, 다음 방향의 재설계 프로젝트다.

- 별도 도메인에서 운영되는 독립 서비스
- 검색 가능한 카드형 개인 아카이브
- 태그 + 컬렉션의 이중 정리 구조
- AI 분석 + 사용자 메모의 결합
- 모바일 저장과 재탐색에 강한 경험

이 문서는 `urlf2`의 1차 설계 기준선으로 사용한다.
